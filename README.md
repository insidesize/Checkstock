# CheckStock - где сейчас товар

Веб-прототип складского учёта для одного магазина с несколькими фулфилментами (ФФ). Менеджер видит, сколько товара физически на каждом ФФ, сколько доступно, что в резерве под FBS и что уже в пути: между ФФ, на склад маркетплейса (FBO) или к клиенту (FBS).

Стек: Python 3.12, FastAPI, SQLAlchemy 2, PostgreSQL 16, React + TypeScript (Vite).

## Запуск

```bash
docker compose up --build
```

Откройте http://localhost:8000. При первом старте создаются таблицы и тестовые данные из задания: ФФ «Север» и «Юг», остатки SKU-101 (10/6), SKU-102 (5/0), SKU-103 (0/4). Повторный старт данные не дублирует. Сбросить всё: `docker compose down -v`.

Swagger с описанием API: http://localhost:8000/docs.

### Без Docker (для разработки)

Нужен запущенный PostgreSQL и база `checkstock` (строка подключения - переменная `DATABASE_URL`, по умолчанию `postgresql+psycopg://checkstock:checkstock@localhost:5432/checkstock`).

```bash
cd backend && pip install -r requirements-dev.txt && uvicorn app.main:app --reload   # API на :8000
cd frontend && npm install && npm run dev                                            # UI на :5173, /api проксируется
```

## Проверки

```bash
docker compose --profile test run --rm tests        # или локально: cd backend && python -m pytest
```

31 тест на PostgreSQL (SQLite не подходит: проверяются блокировки строк и CHECK-ограничения). Тестовая база создаётся автоматически и не трогает рабочую.

| Что проверяется | Файл |
|---|---|
| Учёт после прихода, резерва, отмены, отправки, перемещения, FBO, приёмки; «всего учтено» не меняется при перемещениях | `test_stock_flows.py` |
| Нехватка на ФФ при достаточном общем остатке, нехватка общая, резерв не предлагается как «доступное» | `test_shortage.py` |
| Добавление/переименование/удаление ФФ, удаление с остатком, документы «в полёте» при удалении | `test_ff_lifecycle.py` |
| Повторные подтверждения, ключ идемпотентности, недопустимые переходы, параллельные запросы | `test_idempotency.py` |

Кроме тестов, в интерфейсе на вкладке «Остатки» есть кнопка **«Сверить с журналом»** (`GET /api/audit`): остатки и документы пересчитываются заново по журналу движений и сравниваются. После каждого шага в тестах эта сверка тоже зелёная.

## Как устроен учёт

Товар всегда находится в одном из «мест»:

```
поставщик ─приход→ ФФ: свободно ─резерв→ ФФ: резерв FBS ─отправка→ в пути к клиенту (FBS)
                       │    ↑            └─отмена─┘
                       │    └ приёмка ← в пути между ФФ
                       ├─ перемещение → в пути между ФФ
                       └─ FBO → в пути на склад МП ─приёмка→ склад маркетплейса
```

На каждой паре (артикул, ФФ) хранятся `on_hand` (физически) и `reserved` (резерв FBS); `available = on_hand − reserved` вычисляется, а не хранится, чтобы не разъезжаться. «В пути» считается по документам в соответствующем статусе.

## Ключевые решения

**1. Три слоя данных: остатки, документы, журнал.**
`stock` - быстро читать и блокировать; `documents` - операции с жизненным циклом (статусы); `movements` - неизменяемый журнал, где каждая единица товара переходит из одного места в другое. Журнал нужен не ради красивой истории: по нему `/api/audit` независимо перепроверяет остатки. Остаток меняется только вместе с записью в журнал, в одной транзакции.

**2. Отправка списывает товар с ФФ сразу, приёмка зачисляет.**
Между этими шагами товар числится «в пути» (колонки «Между ФФ» / «На склад МП»), поэтому «Всего учтено» по артикулу не меняется и ничего не «теряется». То же для FBO. Для FBS: резерв только уменьшает «доступно», а физическое списание происходит при отправке заказа.

**3. Повторное подтверждение не списывает товар дважды.**
Подтверждения (принять, отправить, отменить) - это переходы конечного автомата: документ читается `FOR UPDATE`, и если он уже в целевом статусе, возвращается тот же результат с пометкой `already_applied`, а остатки не трогаются. Конфликтующий переход (отменить уже отправленный заказ) даёт 409. Создание документов идемпотентно по `client_request_id`: форма генерирует ключ, и двойной клик или повтор после обрыва связи не создадут дубль. Параллельные запросы закрыты тестами с настоящими потоками.

**4. Нехватка: ошибка с подсказкой, ничего не меняется.**
Если на выбранном ФФ меньше нужного, операция отклоняется целиком (409). Если по всем ФФ товара хватает, ответ содержит `INSUFFICIENT_AT_FF`, недостающее количество и список ФФ, где товар есть, и интерфейс предлагает перемещение одним нажатием. Если не хватает вообще - `INSUFFICIENT_TOTAL`. Автоматически добирать с других ФФ я не стал: это бизнес-решение менеджера (куда и за чей счёт везти), а не системы. Зарезервированный товар в «доступное» не попадает.

**5. Проверка наличия - под блокировкой.**
Строка остатка берётся `SELECT … FOR UPDATE`, и условие «доступно ≥ нужно» проверяется уже под замком. Иначе два одновременных резерва прочитали бы один и тот же остаток и оба прошли бы (это воспроизведено: без блокировки 8 потоков зарезервировали 24 шт при остатке 10, и тест падает). Дополнительно в БД стоят `CHECK (on_hand ≥ 0, reserved ≥ 0, reserved ≤ on_hand)` как последний рубеж.

**6. «Удаление» ФФ = архивация.**
Строка ФФ, остатки и история сохраняются; на вкладке «Склады ФФ» отдельным блоком показано, где числится товар удалённых ФФ. Правило простое: на удалённый ФФ нельзя ничего принимать и резервировать (приход, перемещение «на», FBS), но можно вывезти остатки (перемещение или FBO «с»), а уже созданные документы (резерв, едущее перемещение) доводятся до конца. Имя удалённого ФФ освобождается для нового, ФФ можно восстановить. Жёсткое удаление сломало бы историю и «потеряло» бы товар; запрет удаления при остатке не соответствует заданию.

**7. Приёмка - только полным количеством.** Расхождения при приёмке (принято меньше отправленного) не поддерживаются: это отдельная сущность (недостача, акт) и отдельные состояния. Сознательное упрощение для однодневного прототипа.

## Допущения и что не делалось

- Один магазин: отдельной сущности «магазин» нет. Товаров три (из задания), создание товаров через интерфейс не предусмотрено.
- Один документ = один артикул (без многострочных накладных).
- Нет авторизации и ролей. Нет миграций: таблицы создаются при старте (`create_all`); для продукта нужен Alembic.
- Время в истории показывается в часовом поясе браузера.

## ИИ и проверка результата

Код написан с помощью ИИ-ассистента (Claude); решения по модели учёта (раздел выше) принимались мной. Проверка результата ИИ: складские сценарии покрыты тестами (см. «Проверки»); тест на гонки проверен «от противного» (блокировка отключена - тест падает); интерфейс пройден руками в браузере по сквозному сценарию: нехватка → подсказка → перемещение → приёмка → удаление ФФ → история.
